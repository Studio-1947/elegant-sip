# Elegant Sip — end-to-end gaps list (8 Nov 2026)

Scope: the API (orders, payments, webhooks, auth, admin), the storefront checkout
and order pages, the production Docker/Caddy setup, CI, and the live site at
`https://elegantsip.in`.

How it was checked: code read-through, typecheck, lint, the full API test suite
against real Postgres + Redis containers, the storefront production build, the
OpenAPI drift check, and read-only probes of the live site.

Status key: **Fixed** = changed in this working copy and verified ·
**Open** = still to do. Area tells you who can pick it up in parallel:
`api`, `web`, `ops` (needs the VPS or a dashboard), `business` (needs a decision).

---

## Part A — fixed in this change (not yet committed or deployed)

| # | Severity | Area | Gap | Fix |
|---|---|---|---|---|
| F1 | Critical | api | A single failed payment attempt (`payment.failed` webhook) cancelled the order and released its stock. Razorpay lets the customer retry in the same window, so a successful retry took money for a cancelled order. Payments are live, so this could happen today. | A failed attempt is now only logged; the order stays payable. If nothing succeeds, the 30-minute expiry releases the stock. |
| F2 | Critical | api | A payment captured after the order was cancelled/expired was silently recorded as `already_paid`. The money was taken and nobody was told. | Now recorded on the payment row as `captured`, the webhook event is stored with `refund_required`, and an error log line starts with `REFUND REQUIRED`. The checkout verify endpoint does the same. |
| F3 | High | api | Guest-order access compared token hashes with `===`. If an account is deleted, its orders get a null user and a null hash, so `null === null` let anyone with the order number read the order, its invoice, and call payment verify. | One `guestAccessMatches()` check that requires both hashes to be present, used in all four places. |
| F4 | High | api | Staff could move any order to any status (e.g. unpaid → shipped). Cancelling never returned stock, so every staff-cancelled order permanently lost inventory. | Allowed status changes are now enforced (409 otherwise). Cancelling returns stock and coupon use in one transaction, exactly once. |
| F5 | High | api | Approving a customer's *cancellation* request changed only the request, not the order. The order stayed paid and could still be shipped. | Approving now cancels the order and returns stock. If it has already shipped, staff get a 409 telling them to handle it as a return. |
| F6 | High | ci | `npm run lint` failed (an `any` in `vite.config.ts`). CI was red, and the production deploy only runs after CI passes. | Fixed. Lint is 0 errors (11 warnings remain, see O-list). |
| F7 | Medium | api | Admin rights came from the session, which keeps the role for 30 days. A demoted staff member kept admin access. | The admin role is now checked against the database on every admin request. |
| F8 | Medium | api | If Redis went down, *every* request returned 500, including the catalogue and health checks. | Session lookup failure now means "signed out", and the error is logged. |
| F9 | Medium | api | Limited coupons could be over-redeemed by two simultaneous checkouts. Expired or cancelled orders never gave their coupon use back. | Coupon row is locked during checkout; redemptions are released with the stock. |
| F10 | Medium | api | The Razorpay order-creation call had no timeout and runs while stock rows are locked. A hung call would block checkout for that tea. The Interakt OTP call had no timeout either. | 15 s and 10 s timeouts; a failed OTP call returns a clean 503. |
| F11 | Medium | web | A customer who closed the payment window had no way to pay. The order page only said "awaiting confirmation" until the order expired. | New `GET /v1/orders/:number/payment` and a **Pay now** button on the order page that reopens Razorpay. |
| F12 | Low | api | Password-reset and email-verify links could be used twice by two simultaneous requests. | Consumed with one conditional update. |
| F13 | Low | api | Two identical requests racing on a unique key (e.g. double-submitted checkout) returned 500. | Returned as 409 "already being processed". |
| F14 | Low | api | The order confirmation email said "Your tea is on its way" before anything was shipped, which breaks the site's own honesty rule. | Heading changed to "Payment received — thank you". |
| F15 | Low | api | Replying to a contact-form email replied to the shop itself. | Reply-To is now the customer. |
| F16 | Low | ops | `PENDING_PAYMENT_TTL_MINUTES`, `ORDER_EXPIRY_SWEEP_SECONDS` and `CONTACT_INBOX` in `.env` were silently ignored: the compose file never passed them to the API. A blank `AANGAN_INTERAKT_WEBHOOK_URL` crashed the API at boot. | All passed through; a blank URL now means "unset". |
| F17 | Low | docs | `.env.prod.example` had a garbled header. `AGENTS.md` said to verify `/api/docs`, which correctly returns 404 in production. | Both corrected. |
| F18 | High | api | No reconciliation before expiry (was O4). If the webhook was lost *and* the customer closed the tab before the verify call, the 30-minute sweep cancelled an order that had been paid. | Before expiring, the sweep asks Razorpay for the order's payments (`GET /v1/orders/{id}/payments`). A captured payment marks the order paid (invoice and email as normal). If Razorpay can't be reached, the order is left for the next sweep. An authorized-but-uncaptured payment logs a warning to check auto-capture. |

Tests added: retry after a failed attempt still pays; late payment on an expired
order is flagged; staff cancel enforces transitions, returns stock once, and
respects a revoked admin role; the expiry sweep captures a paid-but-unconfirmed
order, holds an order while the gateway is unreachable, and still expires an
authorized-only payment. **API suite: 50/50 pass** on real Postgres + Redis.
